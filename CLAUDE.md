# Working in this repository

How the lab is built, how to run it, and the design choices the exercises depend on.

## What this is

incidentlab is a local training lab for incident investigation: comparing layers, Little's Law and queueing, tail latency, retry loops, Kafka lag, trend prediction, traces and false leads. Docker Compose runs a small checkout system (Envoy, api, pricing, Postgres, Redis, Kafka, worker) plus Prometheus, Grafana, Tempo and Pyroscope. A controller injects a random fault. The learner investigates with the dashboards, submits an answer and gets a score.

Everything in the repo is English: code, comments, log lines, learner-facing text, Makefile help. The study guide the learners read lives under `docs/`:
- `investigation-guide.md`: RED and USE, the layers, Little's Law, how the lab maps to the guide.
- `foundations.md`: statistics for latency, the latency time scales, Amdahl, USL and the queue models.
- `monitoring.md`: counters and gauges, the PromQL traps, the metrics that lie.
- `methods.md`: methods for the root cause and for working an incident.
- `benchmarking.md`: benchmarking mistakes, open and closed load models.
- `cpu.md`: CPU shares and quotas, CPU busy with no work, off-CPU time.
- `profiling.md`: CPU and off-CPU profiling, and the profiles in this lab.
- `toolbox.md`: the 60-second checklist, crisis tools, and the toolbox mode.
- `capacity.md`: capacity from a ramp test and closed-loop clients, for `make ramp` and `make bench`.
- `network.md`: network math, TCP behaviour you feel in p99, and the network panels.
- `disk.md`: disk math, Postgres and the disk, and the disk panels.
- `runtime.md`: garbage collection, virtual threads, and system time.

Scenario and quiz `doc` fields point at their headings as `Section > Subsection (note)`. `GuideIndex` (`labctl/guide`) maps every `## ` section title to its file, so a section title must be unique across the docs files, and `GuideIndex.where(doc)` is what the "Read again in" line prints. `GuidePointersTest` reads every `docs/*.md`, checks the uniqueness, checks that the index matches the files, and checks that every pointer resolves, so a heading rename or a new section must update the pointers and the index too.

`service/tool/labctl/src/main/kotlin/com/c0x12c/incidentlab/labctl/scenario/catalog/` holds the answers, one file per layer. The README tells learners not to read it.

## Commands

Everything goes through `make`. `make` with no target lists them.

Lifecycle:
- `make up`: build the shared image inside Docker, start everything, then poll `http://localhost:8080/products/1` until api answers (up to about 4.5 min). Copies `.env.example` to `.env` on first run.
- `make down`: remove containers, networks and volumes. This wipes Postgres data, Prometheus data and exercise history.
- `make nuke`: `down` plus delete the built image.
- `make stop`: stop containers, keep volumes.
- `make up-datadog`: same as `up` with the `datadog` compose profile. Needs `DD_API_KEY` in `.env`.

Exercises (each one runs the `labctl` CLI inside the `control` container):
- `make new` with optional `LEVEL=1|2|3`, `TOPIC=async`, `ID=pool_hold`, `FORCE=1`
- `make hint`, `make answer`, `make reveal`, `make clear`, `make status`, `make list`, `make history`
- `make quiz N=50 KIND=numbers|concepts|all`: theory drills from the guide, numeric (`Numbers`) and multiple choice (`Concepts`). Default KIND is `all`. Does not need the lab running.
- `make load X=1.5`: multiply the background load (default 50 rps).
- `make toolbox` with the same options as `make new`: a CLI-only exercise (`labctl new --mode toolbox`). It picks only scenarios with a non-empty `cli`; `make list` tags them `[toolbox]`.
- `make shell`: starts the `toolbox` container if needed and opens `bash -l` in it, which prints `toolbox-help`.
- `make ramp STEP=60`: a capacity ramp (mode `ramp`). The load rises through 50 to 300 rps, `STEP` seconds per step, under a hidden limit. `make answer` then asks the knee, the highest throughput and the limiting resource, scored from Prometheus. Refused unless `make load` is 1.
- `make bench CLIENTS=20 SECONDS=120`: closed-loop clients for a while (mode `bench`, not scored). `make answer` or `make bench` after it prints the 2 minutes before against the bench window.

Development (Gradle lives in `service/`, needs a JDK on the host; Gradle downloads JDK 21 itself):
- `make build` (`./gradlew installDist`), `make test`, `make lint` (ktlint), `make format`.
- One module: `cd service && ./gradlew :tool:labctl:test` or `./gradlew :api:checkout:installDist`.
- One test class: `cd service && ./gradlew :tool:labctl:test --tests '*ExercisesTest*'`.
- `make dashboards` regenerates the Grafana JSON from `service/tool/dashboards` through the built image. Grafana reads the bind-mounted folder, so no restart is needed. Do not edit the JSON by hand.
- `docker compose build control && docker compose up -d api` rebuilds after a code change. All JVM services share one image (`incidentlab-svc:latest`), and only `control` declares its `build:` (the others have `pull_policy: never`), so Compose builds it once. Other services keep the old code until you restart them too.
- `make logs S=api` (empty `S` means all services), `make ps`.
- `make site` opens the handbook (http://localhost:4000, the `site` service).
- The handbook alone: `cd site && npm ci && npm run dev` (Node 22). `npm run build`, `npm run lint`, `npm test`, `npm run check:data`.
- The lab API for `npm run dev`: `cd service && LAB_STATE=/tmp/lab-state.json ./gradlew :tool:labctl:run --args=api` serves it on 8090 with its own state file and no control loop, so no fault is applied. Vite proxies `/api` to 8090. With the lab up, `LAB_API=http://localhost:4000 npm run dev` uses the real API through the site's nginx instead.

Host ports: Envoy 8080 (admin 9901), Grafana 3000, Prometheus 9090, Pyroscope 4040, handbook 4000. They bind to 127.0.0.1 only: Grafana is an anonymous Admin and the handbook can drive the lab, so neither may reach the LAN. Tempo has no host port: traces are read in Grafana. Service ports (api 8000, pricing 8001, worker 8002, loadgen 8003, pgobserver 8004, noisy 8005) are only reachable inside the compose network.

## Architecture

### Request path

loadgen -> envoy:8080 -> api:8000 -> Redis (product cache), Postgres (pool), pricing:8001 (`/price`, `/recommend`), Kafka topic `orders` -> worker (consumer group `order-worker`, 3 partitions) -> Postgres.

loadgen is an open-model Poisson generator per tenant. It makes the root sampling decision for traces (`LOADGEN_TRACE_SAMPLE_RATIO`, default 0.25). Every other service samples with `parentbased_traceidratio` at 1.0, so they follow loadgen.

### Gradle layout (mirrors the service-opstracer conventions)

- `core/`: framework-free libraries. `module-logging` (the `Logging` interface, `info { }` extensions, `logback-base.xml`), `module-utility` (`ResizableGate`, jitter, CPU burner, `retryForever`), `module-faults` (the `Faults` registry), `module-metrics` (Micrometer wrappers with Prometheus names, process and cgroup binders), `module-tracing` (OpenTelemetry span and propagation helpers), `module-database` (Hikari pool, JDBC helpers).
- `shared/`: `module-exception` (`ClientException`, `ErrorResponse`, `CheckoutError`), `module-client` (DTOs and the Retrofit `PricingApi`), `module-infra` (the Micronaut glue every service inherits: `/admin/faults`, `/metrics`, the RED filter, the event loop probe, `AppDatabaseConfig` and `DatabaseFactory`, `AppKafkaConfig`, the error handler).
- `domain/module-checkout/`: `module-api` (interfaces), `module-repository` (the SQL, one `/* q=name */` statement each, timed per call), `module-impl` (the manager, DB sessions, pricing client, cache, Kafka producer, backfill job, admission filter, `CheckoutFactory`).
- Deployables are thin composition roots with an `object Main` and an `application.yml`: `api/checkout`, `api/pricing`, `worker/orders` (the Kafka consumer), `loadgen`, `noisy`, `pgobserver` (flat: a load generator, a batch job and an exporter are neither an api nor a worker), `tool/labctl` (plain Kotlin, no Micronaut), `tool/dashboards`.
- Conventions: `@Factory` classes build the plain classes; the classes themselves are never `@Singleton` unless they are loops or filters. Typed `@ConfigurationProperties` data classes bind `app.*`. Package root is `com.c0x12c.incidentlab`; `core/module-logging` keeps `com.c0x12c.logging`. JDK 21 toolchain (the BLOCKING executor runs on virtual threads). ktlint with the copied `.editorconfig`.

### One image, many launchers

`service/Dockerfile` is a two-stage build: Gradle `installDist` for every deployable, then a JRE image with every distribution under `/run/app/<name>/`. `docker-compose.yml` picks the launcher per service with `SERVICE_LAUNCHER`. A new module needs no Dockerfile change, but it does need a rebuild.

### Continuous profiling

The runtime image downloads the Pyroscope Java agent (`io.pyroscope:agent`, pinned with its sha256 in `service/Dockerfile`) to `/run/pyroscope.jar`. Only api, pricing and worker load it, through `JAVA_TOOL_OPTIONS` and the `PYROSCOPE_*` variables of the `x-profiled` block in `docker-compose.yml`. `PYROSCOPE_APPLICATION_NAME` is the compose service name, so it is the `service_name` label in Pyroscope. The agent runs async-profiler with `itimer` (Docker's default seccomp profile blocks `perf_event_open`), plus allocation (512k) and lock (10ms) sampling, and uploads JFR every 10 s to the `pyroscope` service (grafana/pyroscope 1.x, self-profiling off). Grafana has the Pyroscope datasource (uid `pyroscope`), and Tempo's `tracesToProfiles` points at it with the `process_cpu:cpu:nanoseconds:cpu:nanoseconds` profile type. No span profiling bridge is installed, so Grafana shows no per-span flame graph: a trace links to a profile by service and time range. `docs/profiling.md` is the learner's guide to it.

### What every Micronaut service gets from shared/module-infra

- `GET /metrics` (`PrometheusMeterRegistry` built by hand so no auto binder renames a series). It answers in OpenMetrics when the `Accept` header asks for it, because only OpenMetrics carries exemplars. `CurrentSpanContext` gives the registry the current OTel span, so a histogram recorded inside a sampled span gets a `trace_id` exemplar.
- `GET/PUT /admin/faults`, `POST /admin/reset`.
- `RedMetricsFilter` (just after the TRACING phase, so it runs inside the server span; blocking executor): `http_server_requests_total{route,method,status}`, `http_server_duration_seconds{route,outcome}`, `http_server_inflight`. Paths under `/metrics`, `/admin` and `/health` are skipped.
- `EventLoopRuntime`: `event_loop_lag_seconds` and `onEventLoop { }` to park CPU work on the single Netty event loop thread (`micronaut.netty.event-loops.default.num-threads: 1` in api and pricing).
- `ProcessMetrics` (`process_cpu_seconds_total`, `process_resident_memory_bytes`, `process_start_time_seconds`) and `CgroupMetrics` (`cgroup_*`, read from `/sys/fs/cgroup`).
- `JvmMetrics` (Micrometer's GC, memory and thread binders) and `JfrMetrics` (a JFR `RecordingStream` on `jdk.VirtualThreadPinned` at a 1 ms threshold). `MetricsFactory` binds `JvmMetrics` first, because its filter that gives `jvm.gc.pause` the shared buckets only shapes meters registered after it.
- Tracing comes from `micronaut-tracing-opentelemetry-http` configured with `otel.*` keys in each `application.yml`; the OTLP exporter uses the JDK sender, not OkHttp. `otel.traces.exporter: otlp` must stay set: Micronaut's factory defaults the exporter to none, and then every span is silently dropped.
- `NetstatMetrics` (`net_tcp_*`): the TCP counters of the service's own network namespace, read from `/proc/self/net/{snmp,netstat,sockstat}` at most once per scrape.

`Faults` is a map of defaults plus overrides. Each deployable publishes one `Faults` bean with its own defaults (`CheckoutFaults`, `PricingFaults`, `OrdersFaults`, `LoadgenFaults`, `NoisyFaults`). A key only does something when the service reads it.

### Fault control loop (how an exercise changes the system)

`control` runs `labctl daemon`. Every 3 seconds it:
1. Reads `/state/state.json` (volume `labstate`). Shape: `{active, history, base}`.
2. Builds the override dict per service: `base` (from `make load`) plus `ScenarioCatalog.byId[active.id].faults(params)` (`DesiredState.of`).
3. PUTs that dict to each service's `/admin/faults`. A service not named by the scenario gets `{}`, which resets it.
4. Sets the api container's CPU limit through the Docker socket (`DockerControl`, raw engine API over `docker-java-transport-zerodep`). Base is 2.0 cores; a scenario's `docker` map overrides it.

Step 2 asks the fault sources in `DesiredState.SOURCES` (`FaultSource`: an id and params in, a `FaultSpec` or null out). `ScenarioCatalog`, `RampCatalog` and `BenchCatalog` are the sources, so an id must be unique across them, and `make new` only picks from `ScenarioCatalog`. A mode other than `incident` implements `ExerciseMode` (answer, reveal, hint, status), and `Exercises` hands those commands to it while it is the active mode.

Steps 3 and 4 are `Applier`s (`ServiceFaultApplier` and `ContainerCpuApplier` in `control/Applier.kt`). `ControlDaemon` runs the list that `Main` wires; the CPU applier is only wired when the docker socket exists. Each applier names the `docker` settings keys it applies (`dockerKeys`). At start the daemon writes the keys of its wired appliers to `capabilities.json` beside the state file. `make new` and the API read it and never start a scenario whose rendered `docker` map needs a missing key: a random pick skips it, and its id is refused (`unsupported`). With no file (dev `labctl api`, tests), every key counts as supported. The ramp and the bench do not check it: without the docker socket the ramp's CPU setup has no limit.

`NetemApplier` (also wired only with the docker socket) runs `/run/netem.sh` inside api through the engine API exec endpoint. A scenario asks for it with `docker.api.netem = {target, delay_ms, loss_pct}` (or a list of them); no `netem` key means `netem.sh clear`. The applier skips a tick whose command did not change and runs it again once a minute, so a restarted api gets its shaping back. Only `Services.NETEM_CONTAINERS` (api) is touched, because only api has `cap_add: [NET_ADMIN]`.

`service/docker/netem.sh` contract: `apply <host> <delay_ms> <loss_pct> [...]` resolves each host, builds a `prio` root qdisc on eth0 with one extra band per target from `1:4` up (bands 1 to 3 keep the default priomap, so other traffic is untouched), a netem leaf per band and a u32 filter on the target IP. It is idempotent through `/run/netem.state`. `clear` deletes the root qdisc. Shaping is on api's egress only: the other side never sees the fault.

A third applier, `CgroupApplier`, sets a container's write IOPS limit from `docker[service]["write_iops"]` (a number, or `max` for none; `BASE_DOCKER` gives postgres `max`). The Docker API cannot change `io.max` after creation, so it writes `<disk> wiops=<n>` to `<CGROUP_ROOT>/docker/<id>/io.max` itself (the systemd layout `system.slice/docker-<id>.scope` works too). `BlockDevice` finds the disk: the `st_dev` of `HOST_VOLUMES`, mapped from a partition to its whole disk through `HOST_SYS/dev/block/<maj:min>`. For that, `control` runs privileged with `/sys/fs/cgroup` (rw), `/var/lib/docker/volumes` and `/sys` (ro) mounted under `/host`. When a mount is missing, the applier is not wired and the daemon logs it once.

pgobserver is the fault agent for Postgres: its `/admin/faults` takes `checkpoint_timeout_s`, `checkpoint_completion_target` and `max_wal_size_mb` (defaults are the server's own), and a 3 s loop compares them with `pg_settings` and runs `ALTER SYSTEM SET` plus `pg_reload_conf()` when they differ. All three are reload settings, so no restart. `stats_rows_per_s` (default 0) turns on a writer that rewrites random rows of `review_stats` (1,280,000 rows, fillfactor 50, about 128 MB, created or grown by pgobserver the first time the rate is above 0) once a second. Postgres runs with `shared_buffers=256MB` so the table fits.

The daemon owns fault state. A manual PUT to `/admin/faults` is reverted within 3 seconds. To change behavior, change `state.json` through the `make` commands, or change the scenario.

### Scenario contract (`scenario/catalog/`)

`ScenarioCatalog.all` joins one list per layer: `LoadScenarios`, `EdgeScenarios`, `AppScenarios`, `DatabaseScenarios`, `DownstreamScenarios`, `AsyncScenarios`, `ContainerHostScenarios`, `ProfilingScenarios`, `NetworkScenarios`, `DiskScenarios` and `JvmScenarios`, each an `internal object` with `val all`. A new scenario goes into the file of its `answer.location`, except a scenario that only a profile can solve, which goes into `ProfilingScenarios`. `scenario/Baseline.kt` holds the numbers more than one scenario reads (the tenant mix, `BASE_RPS`, the checkout hold time, the worker capacity, the unit constants); a number only one scenario uses stays private in that file.

Each `Scenario` has: `id`, `title`, `level` (1 to 3), `topics`; `params(random, context)` (context carries `cpuCount`, `productDetailSeconds`, the measured cost of one uncached product query, used to calibrate load, and `tenants`, loadgen's default rate per tenant); `faults(params) -> FaultSpec(services, docker)` runs every daemon tick and `Params.elapsedSeconds` is the time since the start, so a fault can change mid-exercise (`lag_after_fix` rolls the worker back after `fix_after`); `ticket(params)`, `hints` (3), `explain(params)`; `steps` (the investigation trace printed after the explanation); `answer` (`nature`, `location` and `signal` are sets of accepted keys from `Answers`, `cause` one key, `partial` the causes worth 1 point: a visible consequence one step before the root cause); `evidence` (PromQL), `cli` (shell commands that prove the cause without Grafana, run in `make shell`; each entry is one command line that ends with `   # what to read`, finds a process with `$(pid api)`, `pricing`, `worker`, `noisy` or `postgres` (never a bare `pgrep`: with `pid: host` it also matches other projects' containers on the VM), reaches a cgroup with `cg PID`, Postgres with `PGPASSWORD=lab psql -h postgres -U lab lab -c`, and a counter with two `curl -s http://api:8000/metrics` readings; the explanation prints it after the PromQL in every mode), `doc`; optional `marker(params)` (real Grafana annotation 0 to 3 minutes before start), `decoy` (probability of a fake annotation between 10 minutes before and 1 minute after start) and `baseLoad` (the draws are calibrated at 50 rps, so `make new` skips the scenario and refuses its id unless the load is 1; the load may still change during the exercise). `Answers.CAUSES` also holds `DISTRACTORS`, causes no scenario has, and some causes belong to two scenarios (`pool_exhausted`, `single_thread_cpu`, `client_timeout`), so the cause list is not a copy of the catalog.

Scoring: nature 1, location 1, signal 1, cause 2 (partial 1), minus 0.5 per hint; 5 points max. After scoring, `make answer` asks for a one-line note, kept in history with the missed questions. `make new` skips the last 5 played ids. `ScenarioCatalogTest` renders every scenario with a seeded random and checks the fault targets, so run it after any catalog change.

The quiz data sits next to the docs file it drills: `quiz/numbers/InvestigationNumbers.kt` (the generators) and `quiz/concepts/InvestigationConcepts.kt` (the questions) for `docs/investigation-guide.md`, `FoundationsNumbers` and `FoundationsConcepts` for `docs/foundations.md`, `MonitoringNumbers` and `MonitoringConcepts` for `docs/monitoring.md`. `quiz/numbers/Formulas.kt` holds the closed forms the foundations drills share (means, Amdahl, USL, the queue waits), so `FormulasTest` can check them with known values. `Numbers.generators` and `Concepts.all` join the per-file lists with `+`, and `GuidePointersTest` checks that the drills cover every subsection. `docs/profiling.md` has `ProfilingNumbers` and `ProfilingConcepts`. Every other docs file follows the same naming. `CapacityNumbers` and `CapacityConcepts` drill `docs/capacity.md` (the ramp and the bench).

### Metric conventions

- Declare Micrometer names without the `_total` the Prometheus registry appends; `LabHistogram` is a Micrometer `Timer` with the shared `LatencyBuckets`, and its names already end in `_seconds`. Do not use a `DistributionSummary` for latency: Micrometer rounds a summary value up to a whole number before it picks the bucket, so every sub-second value lands in the 1.0 bucket (`LabHistogramTest` guards this). Use `LabCounter`, `LabHistogram`, `LabGauge` for label-keyed families.
- `http_client_*`: api calling pricing (`target`, `route`). `db_client_session_seconds{op}`: pool wait plus hold. `db_client_duration_seconds{query}`: the statement only. `db_pool_*`, `app_admission_*`: software resources inside api.
- `pg_*` come from pgobserver, which names queries from the `/* q=name */` comment at the start of each SQL string in `module-repository`. A new statement must carry that comment or it will not show up.
- `kafka_*`: produce (api) and consume, lag, retries (worker). `client_*`: loadgen. Prometheus job names equal compose service names.
- `app_lock_wait_seconds`, `app_lock_waiting`, `app_lock_held_seconds_total` (rate() is utilization): api's inventory lock. `app_price_fallback_total`: checkouts priced without pricing. `orders_value_total{tenant}`: sum of order totals, so `orders_value_total / orders_total` is the mean order value. `noisy_forks_total`: short processes noisy started.
- `client_closed_clients`: the closed-loop clients loadgen runs. 0 means the open model.
- `net_tcp_*`: per-service TCP counters from `NetstatMetrics` (`out_segs`, `retrans_segs`, `active_opens`, `passive_opens`, `attempt_fails`, `estab_resets`, `timeouts`, `loss_probes`, `lost_retransmit`, `syn_retrans`, `listen_overflows` as counters, `current_established` and `time_wait` as gauges). Each container has its own network namespace, so node-exporter cannot give these. `http_client_connections_total{target}`: TCP connections api opens to pricing (OkHttp `connectStart`).
- Disk and Postgres internals, from pgobserver: `pg_wait_events{type,event}` (mean backends waiting, sampled from `pg_stat_activity` every 100 ms, idle `Activity` and `Client` waits and chosen `Timeout` pauses left out), `pg_checkpoints_total{kind=timed|requested}`, `pg_checkpoint_write_seconds_total`, `pg_checkpoint_sync_seconds_total`, `pg_buffers_checkpoint_total` (from `pg_stat_bgwriter`, Postgres 16 names; the checkpoint counters move when a checkpoint ends, and write time includes the pauses that spread it), `pg_wal_bytes_total`, `pg_wal_fpi_total`, `pg_wal_syncs_total`, `pg_wal_sync_seconds_total` (from `pg_stat_wal`; the sync time needs `track_wal_io_timing`, which compose turns on with `track_io_timing`).
- `noisy_fsync_total`, `noisy_fsync_seconds_total`: noisy's disk writer. The host disk comes from node-exporter's `node_disk_*` (whole disks only by default).
- `jvm_*` (api, pricing, worker): `jvm_memory_used_bytes{area,id}` and `jvm_memory_max_bytes` with the Serial pool names `Eden Space`, `Survivor Space`, `Tenured Gen`; `jvm_gc_pause_seconds_bucket{gc,action,cause}` (`gc="Copy"` young, `gc="MarkSweepCompact"` full) on `LatencyBuckets.LATENCY`; `jvm_gc_live_data_size_bytes` (old gen after a full GC, 0 until the first one); `jvm_gc_memory_allocated_bytes_total`, `jvm_gc_memory_promoted_bytes_total`, `jvm_threads_*`. `jvm_virtual_thread_pinned_total` and `jvm_virtual_thread_pinned_seconds_total` come from JFR. `cgroup_cpu_mode_seconds_total{mode="user"|"system"}` is cgroup v2 only (0 on v1). `app_retained_bytes` is the GC-pressure store in api.
- Dashboards: `Board.heatmap(title, metric, selector)` draws `sum by (le) (increase(<metric>_bucket[RI]))` with `format: heatmap` and `calculate: false`, so Grafana shows the Prometheus buckets as they are.

### Design choices the exercises depend on

Changing one of these breaks the scenario named in brackets:
- `AdmissionFilter` (FIRST phase) runs before `RedMetricsFilter` (just after TRACING), so queue time shows at Envoy, not at api. [`queue_before_app`]
- A latency histogram gets exemplars only if it is recorded while its span is current. The RED filter, the worker's `kafka.consume` span and loadgen's root span all record inside their span. Record a new histogram the same way or its panel shows no dots.
- `ApiGates.pool` is a `ResizableGate` in front of the real Hikari pool (max 24). `pool_max` default is 4. [`pool_hold`, `db_lock`]
- A healthy checkout holds its connection about 50 ms: `price_work_ms` (default 45) is app work after loading prices, outside any transaction, so Postgres stays idle. At 15 checkouts/s that is about 0.8 connections, so a pool of 1 saturates and a 4x surge fills the pool of 4. [`pool_shrunk`, `global_surge`, `pool_hold`]
- CPU burn runs through `EventLoopRuntime.onEventLoop` on the single Netty thread. api and pricing both have `cpus: "2.0"`, so one saturated thread shows as half the limit with no throttling. [`single_thread_cpu`, `pricing_cpu`]
- loadgen multiplies `rate_multiplier` (what `make load` sets) with `surge_multiplier` (what a scenario sets), so a surge exercise keeps the learner's load setting. [`global_surge`]
- `MemoryLeak` allocates off heap with `Unsafe`, so the kernel OOM killer ends the process, not a Java `OutOfMemoryError`. api has `mem_limit: 768m` and `memswap_limit: 768m`, and its `JAVA_OPTS` in compose pin the heap at `-Xmx256m` (pricing and worker keep the Dockerfile's `MaxRAMPercentage=50`). With the profiler agent and JFR, api idles at about 450 to 500 MB, so the leak fills the last 270 to 300 MB. Without the swap cap, Docker allows twice the limit as swap, and the api swaps and slows down instead of being killed. [`oom`, `slow_leak`]
- Envoy has `healthy_panic_threshold: 0`, so it returns 503 itself when api is unhealthy. A 503 from `/health` is an immediate failure for Envoy (`unhealthy_threshold` does not apply), so the share of 503s is about `health_fail_prob`. [`lb_no_healthy`, `lb_flapping`]
- The controller sets the api CPU limit from a base of 2.0 cores; the throttle scenarios draw 0.10 to 0.14 cores, because api averages about 0.073 cores at 50 rps (p95 per minute 0.079). That uses 53 to 73% of the quota with 16 to 45% of periods throttled. At 0.08 the quota is 82% used and p99 nears 2 s, and at 0.07 it saturates. [`cpu_throttle`, `cpu_credits`]
- `noisy` has `cpu_shares: 65536`. [`noisy_neighbor`]
- No index on `reviews.product_id`; the Redis cache keeps `product_detail` cheap. The cache key includes the TTL, so a config change starts with an empty cache. [`cache_miss`, `tenant_spike`]
- The worker processes each partition in order and retries a failed message for ever. [`poison_message`, `consumer_backlog`]
- `cpu_credits` sets no fault until `credit_seconds` have passed, then lowers api's CPU quota like `cpu_throttle`. The lab has no hypervisor, so the quota stands in for a burstable VM at its baseline. [`cpu_credits`]
- The worker polls Kafka with `poll_ms` (default 500), read on every poll. 0 is `poll(Duration.ZERO)`: the loop spins on one core while lag stays at 0. [`busy_poll`]
- `lock_ms` (default 0) makes every checkout take one fair `ReentrantLock` in `InventoryCache` before any DB session or pricing call. Hold times are exponential around `lock_ms`, so with Poisson arrivals the lock is M/M/1 and the explanation's numbers hold. Above 90% utilization the p99 passes loadgen's 3 s timeout. [`app_lock`]
- `price_fallback` (default false) turns a `DownstreamException` from `/price` into a 200 at the list prices, without pricing's 5% discount. A read timeout counts as one (`outcome="timeout"`). `unexplained_win` slows `/price` to 250 to 400 ms at the start, then after 120 s sets `pricing_timeout_s` to 0.15 with the fallback: every call times out, so /checkout gets faster and every order loses the discount. The jitter must keep the fastest call above the timeout. [`unexplained_win`]
- `fork_rps` (default 0, cap 200) makes noisy start and reap `/usr/bin/true` that many times a second. [`fork_decoy`]
- `render_ms` (default 0) runs `ReceiptRenderer` on every /products and /checkout: Jackson re-serialises the response until the budget is spent, on the request's own virtual thread, never on the event loop. The budget is thread CPU time on a platform thread and wall time on a virtual thread (the JDK reports no CPU time there, and a computing virtual thread is not preempted). There is no span around it, so a trace shows only self time in api and the CPU profile names the code. Virtual threads share one carrier per core of api's 2-core limit, so the drawn 24 to 30 ms makes 1.2 to 1.5 cores at 50 rps and p99 rises on every route. [`hot_code_path`]
- The `toolbox` service (`config/toolbox`, its own Ubuntu 24.04 image) runs with `pid: host`, `cgroup: host`, `privileged: true`, `/sys/fs/cgroup` read-only and the docker socket, on the compose network. Every `cli` entry relies on that: host PIDs from `pid SERVICE` (the container's `.State.Pid` from the docker socket, `incidentlab-<service>-1`, project from `COMPOSE_PROJECT`), absolute paths in `/proc/PID/cgroup` (read by `cg`), `dmesg`, `nsenter`, and service names. It is root on the VM, so it stays a local lab tool. `perf` is a wrapper that runs the installed build whatever `uname -r` says, and tracefs is mounted at start for bpftrace; both depend on the VM kernel and may fail on Docker Desktop (`kernel-check`). [every scenario with `cli`]
- The ramp drives `surge_multiplier`, so its steps are only right with `rate_multiplier` at 1. It refuses to start otherwise, and it pins `rate_multiplier` to 1 while a step runs, so a `make load` during the ramp waits until the ramp is over. Each hidden limit fills inside 50 to 300 rps (pool 2, 3 or 4, api at 0.2 or 0.3 cores, using `API_CORES_AT_BASE`). The other setups open the pool to 24, because the default pool of 4 fills at about 267 rps. [`ramp`]
- loadgen's `closed_clients` above 0 stops every open arrival, crawler included, and runs that many clients with no think time. A client that is no longer wanted finishes its request first. [`bench`]
- netem drops are silent to TCP, and a /price request usually fits in one segment, so a lost request waits for the tail loss probe or the RTO (200 ms floor on Linux). pricing never sees the lost copy, so its p99 stays flat while api's retransmit counters rise. [`packet_loss`]
- A healthy checkout makes 1 price query plus 3 round trips for the order (INSERT order, INSERT items, COMMIT). `rtt_amplified` adds a 3 to 8 ms delay towards Postgres and picks `n_plus_one` from the delay so the pool lands at 2.1 to 2.9 of 4 connections. A round trip costs api the delay plus about 1.8 ms (measured: 0.94 ms of mean query time became 4.8 ms with a 3 ms delay), and the model in `NetworkScenarios.inUse` uses that cost. Changing `price_work_ms`, the pool size or the order writes moves that range. [`rtt_amplified`]
- `pricing_keepalive: false` sends pricing calls through a copy of the OkHttp client whose pool keeps no idle connection, so api closes each connection first and keeps the TIME_WAIT socket (`KeepAliveSwitchTest` proves both). A `Connection: close` request header would make pricing close first instead, and the TIME_WAIT would move to pricing. [`no_keepalive`]
- noisy's fsync writer (`fsync_mb_per_s`), pgobserver's checkpoint settings and its `review_stats` writer stay without a scenario: a laptop SSD absorbs them, so commit latency moved on one run and not on the next. A throttled volume would make them reliable. `disk_io_contention` and `checkpoint_bursts` are distractors until then.
- The IOPS limit is a cgroup `io.max` line on the postgres container, written by `CgroupApplier`. The kernel holds throttled I/O before the device, so node-exporter shows a low await and busy share while Postgres waits on `IO / WALSync`. [`iops_limit`]
- `HeapPressure` keeps `retain_mb` of 16-byte objects in one array and each request writes `churn_kb` of new ones over random slots, so objects live tens of seconds, get promoted, and die in the old generation. With api's 256 MB Serial heap (old gen 170 MB), 70 to 85 MB at 48 to 64 KB per request gave full GCs every 12 to 50 s with 120 to 220 ms pauses on the host JDK. Many small objects, not a few big arrays, make the pause long: a full GC's cost follows the live object count. On the live lab (with the profiler agent) a full GC came about every 22 s with a pause p99 near 0.39 s. A pause stops Netty's event loop too, so a request that arrives during it waits in the socket buffer, before `RedMetricsFilter` starts its timer: the pause shows in Envoy's p99.9, not in api's own histogram. [`gc_pressure`]
- `pin_db` runs the checkout DB sessions and a `pin_hold_ms` sleep inside `synchronized` on a request-local object (`LegacyOrderCache`). On JDK 21 that pins the virtual thread, and api has 2 carriers (one per core), so checkouts keep them 15 × (50 + hold) / 2000 busy: the scenario draws a hold of 45 to 62 ms for 71 to 84%. The 50 ms is the pinned DB work (the 45 ms `price_work_ms` sleep plus the queries). Above 100% the carrier queue grows without end, /health stalls with it, and Envoy marks api unhealthy, so keep it under about 90%. `LegacyOrderCacheTest` proves the mechanism in a forked JVM. JDK 24 or later removes it (JEP 491). [`vthread_pinning`]
- `debug_log_lines` writes DEBUG lines through `SupportTrace`, whose logger api's `logback.xml` sets to DEBUG. The console appender flushes every line, so each one is a write syscall under the appender lock. api's json-file log rotates at 3 × 20 MB so the exercise cannot fill the disk. Measured at 2,000 lines per request: about 1.4 µs of system and 1.2 µs of user CPU per line, so 2,000 to 3,000 lines give 0.14 to 0.21 cores of system time, about 5 to 8 ms more CPU per request, and p99 up on both routes from the appender lock. [`sync_logging`]

### The handbook site (`site/`)

- Vite, React 19, TypeScript, React Router with browser routes. `site/Dockerfile` builds it with the repo root as context (`site/Dockerfile.dockerignore` lets in only `docs/`, the Makefile, docker-compose.yml, README, CLAUDE.md, Answers.kt and the scenario catalog files), and nginx serves it with an SPA fallback. The `site` service maps it to host port 4000.
- Nothing on the site is copied by hand. `scripts/prebuild.ts` runs before `npm run dev` and `npm run build`. It reads `docs/*.md` (GitHub slugs for the heading ids, so a `Section > Subsection` pointer links to `/guide/<file>#<slug>`), the Makefile (the `target: ## help` lines, the `# -----` groups, the URLs `wait` prints), docker-compose.yml, README (the lede and the first list, for Home) and CLAUDE.md (the docs file notes). It writes `site/src/generated/`, which git ignores.
- The catalog, the quiz counts, the scoring and the defaults come from `labctl export`, committed as `site/src/data/lab.json`. Regenerate it after any change to the catalog, the drills, `GuideIndex`, the scoring or a default: `cd site && npm run export:lab` (it runs `./gradlew :tool:labctl:run --args="export <absolute path>"`, so Gradle picks JDK 21). `npm run check:data` fails when the committed file differs from a fresh export.
- No spoilers. Per scenario the export holds only id, title, level, topics and the toolbox flag, the same as `make list`. The guide pointer stays out: it names the cause, and the CLI only prints it after the answer. `LabExportTest` checks the keys and scans for cause and signal keys, answer labels, guide pointers, tickets, hints, steps, explanations, evidence and cli lines. `test/spoilers.test.ts` also checks that no scenario's guide pointer is in lab.json or `dist/`. `npm run build` ends with `scripts/check-bundle.ts`, which reads the keys from Answers.kt and fails if one is in `dist/` (a key that is also a scenario id, or that the docs print, counts as public). It also fails if a scenario's guide pointer is in `dist/` (`scripts/lib/spoilers.ts`, shared with `test/spoilers.test.ts`). Never add a field or a page that shows a cause, signal, location, nature, ticket, hint, explanation, evidence or cli command.
- The request path diagram places its nodes in `src/lib/topology.ts`. Their facts come from docker-compose.yml, and `test/compose.test.ts` checks that every node is a compose service and that each hop named by a compose variable matches it.
- `scripts/lib/groups.ts` groups the guide files. `test/groups.test.ts` fails when a docs file has no group.
- The Play page and the interactive quiz drive the lab through the `labctl daemon` HTTP API: `src/lib/api.ts` is the typed client (every POST sends `Content-Type: application/json` and `X-Lab-Client: web`), and `src/lib/lab.tsx` polls `GET /api/health`. With no lab, those pages say `make up` and the rest of the site still works. nginx proxies `/api/` to `control:8090`, and `npm run dev` and `npm run preview` proxy it to `LAB_API` (default `http://localhost:8090`).
- `LAB_MOCK=1 npm run dev` serves a fake lab from `test/mock-lab.ts`, the same one the msw tests use. Every key and text in it is made up, and a spoiler test checks it never reaches `dist/`.
- The Play page holds only the `ActiveView` until the answer or the reveal comes back, so no scenario text can show early. Only `src/lib/api.ts` may call the answer, reveal and quiz-answer endpoints (`test/spoilers.test.ts` checks it).
- The Grafana links read the dashboard uids and the datasource uids from `config/grafana` at build time. Explore links use the Grafana 11 form `/explore?schemaVersion=1&panes=...&orgId=1`.

### The lab API (`labctl daemon`)

The daemon also serves a JSON API for the handbook, on `LAB_API_PORT` (8090) with the JDK `HttpServer`. The site's nginx proxies `/api/` to `control:8090`, and 8090 is not published to the host. The decisions live in engines that return data: `ExerciseEngine` (incident and toolbox), `RampEngine`, `BenchEngine` and `QuizSessions`. `Exercises`, `RampExercise` and `BenchExercise` only prompt and print, and `api/LabApi` only checks input and writes JSON, so the CLI and the web score the same way. Every POST needs `Content-Type: application/json` and `X-Lab-Client: web`. OPTIONS is a 403 and no CORS header is ever sent, so another origin cannot drive the lab. Before the answer, no response shows a scenario's id, title, answer, explanation, steps, evidence, cli or guide pointer: `ActiveView` has no field for them, and `NoSpoilerTest` opens every scenario through the API to check. The CLI and the API both write `state.json`, so `StateStore` holds an exclusive lock on `state.json.lock` around every read-modify-write. The contract is `service/tool/labctl/API.md`.

### Data and state

- `config/postgres/init.sql` runs only when the `pgdata` volume is created. Schema changes need `make down` first.
- Exercise state and history live in `state.json` on the `labstate` volume. `make down` deletes it. `ActiveExercise` and `HistoryEntry` carry `mode` (`incident`, the default, or another mode: `toolbox`, `ramp`, `bench`); a file written before the field existed still loads.
- Grafana runs as anonymous Admin. Datasources are provisioned (Prometheus uid `prometheus`, Tempo uid `tempo`, Pyroscope uid `pyroscope`). Profiles are read in Explore > Pyroscope or at http://localhost:4040, and the USE board ends with CPU flame graphs of api and pricing. Prometheus exemplars link to Tempo by `trace_id`. Dashboards come from `config/grafana/dashboards/`, generated by `tool/dashboards`.
